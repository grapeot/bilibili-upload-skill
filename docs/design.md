# 设计说明

本文记录 bilibili-upload-skill 的目标、边界、架构和安全规则。使用方法见 `README.md` 和 `skills/bilibili-upload/SKILL.md`。

## 目标

把「把一个本地视频投到自己的 B 站账号」拆成两半：机械的部分交给 agent，判断和责任留给人。

agent 负责的是重复、易错、但不需要判断的操作：选视频文件、清掉 B 站自动带入的文件名标题、逐个输入标签、把多行简介写进富文本编辑器、选创作声明和分区、上传封面和字幕、录入章节、写粉丝动态，最后把表单读回来逐项核对。

人负责三件事：登录（扫码）、看一眼填好的表单、亲手点「立即投稿」。

## 非目标

- 不做无人值守或批量投稿，也不做录播搬运。这类场景有现成的命令行工具（见下文「其他路线」），风险模型不同。
- 不自动登录，不读取、不导出、不打印 cookie。
- 不点击任何提交类按钮：「立即投稿」「存草稿」「提交」「投稿」一律不点。
- 不修改账号设置、收益、充电、商业推广、联合投稿。

## 为什么用可见浏览器

B 站没有面向个人 UP 主、开箱即用的官方投稿 API。官方开放平台的投稿接口需要开发者认证和应用审核；社区的非官方接口方案能用，但要把登录凭据交给脚本保存，并且有限流和账号风险。

可见浏览器路线的好处是：登录态始终留在人自己的 Chrome profile 里；agent 做的每一步人都能在屏幕上看到；最后一步由人完成，出错的代价最小。代价是依赖页面结构，B 站改版后需要更新选择器。本项目把所有选择器集中在一处，并让工具在选择器失效时明确报告是哪一个，而不是静默跳过。

## 架构

```text
人                     agent / CLI                          Chrome（可见，持久 profile）
 │                       │                                      │
 │                       │ bili-upload open ──── 启动 ─────────▶│ 只监听 127.0.0.1:<port>
 │ 扫码登录 ────────────────────────────────────────────────────▶│ 登录态写入本机 profile
 │                       │ bili-upload status ── CDP 只读 ─────▶│ 只返回布尔值
 │                       │ bili-upload fill（默认 dry-run，打印计划）
 │                       │ bili-upload fill --execute ── CDP ──▶│ 新标签页：选文件、填表、读回
 │                       │ 断开连接（不关浏览器）                │ 标签页停在「立即投稿」可见处
 │ 核对、点「立即投稿」 ─────────────────────────────────────────▶│
```

Playwright 通过 `connect_over_cdp` 接入由 `open` 启动的那个 Chrome。脚本结束时只断开连接，不调用 `browser.close()`，所以窗口和登录态都会保留。

模块划分（实现阶段落地）：

| 模块 | 职责 |
|---|---|
| `selectors.py` | 唯一的选择器表；每个条目带用途说明 |
| `guard.py` | 点击守卫：所有点击都经过它，命中提交类按钮就抛异常 |
| `meta.py` | 读取并校验投稿元数据 JSON，路径相对元数据文件解析 |
| `plan.py` | 由元数据生成执行计划（dry-run 的输出） |
| `browser.py` | `open` / `status`：启动可见 Chrome、只读登录检查 |
| `fill.py` | `fill --execute`：按计划操作页面、读回核对 |
| `cli.py` | 命令行入口，每个命令向 stdout 输出一个 JSON 对象 |

## 安全规则

这些规则是本项目的不变量，任何改动都不能破坏。

1. **最后一步永远由人点击。** 工具找到「立即投稿」只为把它滚动到视野内。点击守卫在代码层面拒绝点击文本或类名像提交、存草稿的元素，测试会覆盖这一点。
2. **选择文件就是开始上传。** 把视频交给页面上的文件输入框后，B 站会立刻开始上传，这时稿件还没有发布，但服务器上已经有了文件，也可能生成草稿。因此 `fill` 默认是 dry-run，只打印计划；必须显式传 `--execute` 才会选文件。调用方在传 `--execute` 之前，应确认视频所有者已经授权上传这一个具体视频。
3. **不自动登录。** 未登录时工具只报告状态，提示人在窗口里扫码。工具不接收账号、密码、短信验证码或 cookie。
4. **登录态只留在本机。** 浏览器 profile 默认放在仓库外或 `.local/` 下，目录权限 0700，并已写入 `.gitignore`。工具不打印、不导出 cookie；`status` 只输出布尔值和页面 URL。
5. **只连自己启动的浏览器。** CDP 端口只绑定 127.0.0.1。`open` 发现端口或 profile 已被占用时会拒绝启动，不接管人正在用的浏览器。
6. **不留个人数据。** 截图、DOM 快照、投稿元数据、视频和字幕都不进仓库。文档和测试只用占位路径与合成数据。

## 选择器维护

B 站投稿页是一个微前端（`<micro-app>`），表单元素在普通 DOM 里，CSS 选择器可以直接选到。但类名会随改版变化。应对方式：

- 所有选择器只在 `selectors.py` 里定义，其他模块按名字引用。
- `fill --execute` 每一步先确认选择器能匹配到元素；匹配不到时在结果 JSON 的 `missing_selectors` 里写出名字和选择器字符串，并跳过这一步，而不是猜一个元素去点。
- 填完后逐项读回（标题输入框的值、标签列表、简介文本、分区和声明的显示文本、章节列表等），与元数据对比，差异写进 `mismatches`。

## 其他路线

- **社区命令行工具**（例如 biliup）：支持扫码登录后保存 cookie 文件、批量和无人值守投稿，适合录播类场景。它走的是非官方接口，需要接受相应的账号与服务条款风险。
- **官方开放平台**：提供服务端投稿接口，需要开发者认证、应用审核和 UP 主 OAuth 授权，适合机构，个人偶尔投稿不划算。
- **本项目**：适合个人、低频、需要人把关的投稿。
